# 煤矿排水设备故障风险预警平台 · Equipment-Warning

一句话：把井下排水设备的台账、遥测和现场填报合成一个风险分，告诉你**今天该管哪几台、为什么高、怎么降、什么时候检修**，并能就结果追问大模型。零构建、单机能跑、局域网可访问。

代码目录：本仓库下的 `设备风险预警平台/`，**这是唯一的开发主目录**（双击其中的 `启动.command` 即可运行，Windows 用 `Windows启动.bat`）。桌面上另有一份同名旧目录 `~/Desktop/合同提醒系统或平台/设备风险预警平台/`，它是加固前的快照，已不再同步维护，等确认可清理后移入废纸篓（红线：不直接 `rm`）。

  `cd 设备风险预警平台 && python3 -m venv .venv && .venv/bin/pip install pandas scikit-learn openpyxl`。

## 从台账到模型的闭环

1. 导入设备台账、运行遥测和工作维修日志（`.xlsx` 与多种 CSV 同一条路）。
2. 系统校验并读取最新遥测，用当前 HistGradientBoosting 模型预测设备本身风险，再与工况合成综合风险。
3. 概览的归因与治理页签汇总风险设备、共同因素与建议；AI 助手可参考近期维修日志补充——**日志是历史记录，AI 不把它当成已确认故障**。
4. 在「今日报告」逐台核查，记录故障原因、处置办法、核查人。传感器数据修正只作为原值 / 核实值留痕，**不改写原始遥测**。
5. 「确认故障」与「已检查未发现故障」进入已审核样本；「数据异常」与「待核实」不会被当成训练标签。
6. 在「模型训练中心」另行发起批量重训练（HGBT 不支持 `partial_fit`），评估通过后只生成**待审批候选模型**，管理员发布才成为当前版本；历史版本保留，支持回滚。

## 风险是怎么算出来的

两路独立合成，`risk = 1 − (1 − raw_risk) × (1 − cond_risk)`：

- **设备本身（raw_risk）**：`histgb_model.joblib`（HistGradientBoosting）吃 9 个物理量——类型、额定电压/电流/功率、环境温度、设备温度、电流、累计运行小时、距上次检修小时。模型文件缺失时只用工况评级，页面会红字提示。
- **现场情况（cond_risk）**：7 项加权——环境严酷度 18%、湿度 22%、粉尘 16%、淋水 6%、近三个月故障 20%、检修频率不足 12%、负载率 6%。这一路可以精确重算，所以「把粉尘降一级，风险从 44% 降到 36%」这类结论是真数字，不是估的。
- 分级：正常 / 关注 / 预警 / 报警 / 无数据，阈值集中在 `ai_analyze.py` 的 `TH` 里，便于和工艺人员一起校订。
- 检修排期日期：报警=今天起 3 天内，预警=14 天内，关注=按每台自己的「计划检修频率(次/季)」与「距上次检修小时」倒推到期日（区间取最早—最晚，已过期的另标"N 台已到期"），无遥测的不给日期。

## 台账导入支持的格式

台账页「导入数据」直接选文件，先看文件头几个字节再决定怎么读，不看扩展名：`PK` 开头按 Excel 原文件（`.xlsx`）解，其余按文本解。所以 Excel 存的 `.xlsx`、逗号 / 分号 / Tab / 竖线分隔的 CSV、GBK 编码的 CSV 都能直接导；把文本改名成 `.xlsx` 也照样走文本这条路，不会硬报"文件打不开"。97-2003 的 `.xls`（OLE 头）会挡在提示上，让你另存为 `.xlsx` 或 CSV。

`.xlsx` 走服务端 openpyxl 解析（`data_only` 取公式的缓存值，取不到就当空），日期单元格、`2024/5/6`、`2024.5.6`、带时间的 `datetime` 一律收成 `YYYY-MM-DD`，数字单元格不会变成 `6.0`，1904 纪元的表也按表里的日期落库；报错的行号是 Excel 里看到的那一行，表头上方的空行、中间被删空的行都占位。

两种格式共用一套校验与预检：表头别名（编号/名称/类型…）都认，一次最多 500 行，多张工作表只读第一张并在结果里点名是哪张。**同一份数据走 Excel 和走 CSV 的预检结果逐字段一致**——Excel 只是把表读成行，字段含义、新增/覆盖/跳过/失败的口径没有第二套。先「预检」看汇总和逐行错误，确认无误再「导入」。

## 模型闭环这一轮新加的输入闸

`feature/ai-risk-report` 多了维护日志、日报核实、模型中心三条写入路径。平台上没有任何登录（局域网要用，见下面「已知边界」），所以每一条都按"输入不可信"来堵：

| 入口 | 闸 | 为什么要加 |
|---|---|---|
| 维护记录（确认入库 / 编辑保存） | 七个字段各自限长（正文 5000、结果 500、人员 300、设备 200、地点 100、日期 40、原始日志 5000），正文非空，工作日期必须 `YYYY-MM-DD` | 这两条路以前各写各的校验，编辑那条干脆没有——一条几 MB 的正文能直接写进库里。现在两条路都走 `equipment_db.clean_work_record` 这一个闸 |
| 维护记录（批量） | 单次最多 500 条 | 一次请求塞十万条，等于拿请求体喂磁盘 |
| 工作日志解析 | 识别出的记录数超过 500 条就报「请分批粘贴」 | 解析是纯正则 + CPU，一条超长日志能把那个 worker 占满 |
| 模型训练 | 两次训练至少间隔 60 秒 | 每次都要重建数据集并全量重拟合；没有登录，重复点一下就是白吃一轮 CPU、白留一份记录，所以按时间闸住，不指望前端把按钮禁用住 |
| 模型训练 | 评估未通过的候选**不落盘** | `candidate_rejected` 既不能发布（只认 `pending_approval`）也不能回滚（只认 `published`），文件写出来永远没有引用方，每点一次白占几百 KB |
| 日报核实 | 编号 ≤80、采样时间 ≤40、五个自由文本 ≤1000，结论必须落在四种之一，故障/无故障/数据修正各自的必填项齐了才收 | 这些字段会原样显示在日报页与模型中心 |
| 反馈样本 | 说明 ≤1000、人员 ≤80，标签走白名单 | 同上 |

前端也同步补了 `maxlength`（维护记录的解析草稿与编辑表单），但**闸在服务端**——界面那层只是少一次来回，不算安全边界。

## 已知边界与待办

- 服务监听 `0.0.0.0` 且免登录，是按"局域网要用"的要求保留的；**不要直接暴露到公网**，需要时前置反代加认证。
- 单机 SQLite，没有多用户与权限体系；台账并发写入做了文件锁与串行化，但不做跨机器同步。
- 模型闭环这几条路留下的边界（都不是漏洞，是没改的行为）：日报 upsert 按「报告日期+编号+采样时间」整行覆盖，再存一次会盖掉上一版，不保留历史；`report_date` 不做日历合法性校验，`code` 也不校验是否在台账里——但日报页只按台账设备取行，越界的编号存进去也渲染不出来；`model_feedback_samples` 是每台设备每采样时间一行，随真实遥测体量增长，暂无清理策略；`models/*.joblib` 用 pickle 反序列化加载，信任边界是「只有本进程写进 `models/` 的文件」，接口没有接受模型路径的入口。
